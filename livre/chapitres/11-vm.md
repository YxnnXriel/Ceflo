## 11.1 Trente lignes qui calculent

Le compilateur du chapitre 10 produit des chunks. Pour l'instant, personne ne
les exécute. On va écrire la boucle qui le fait, et on va commencer petit :
une VM de trente lignes, dans un fichier d'essai, qui ne connaît que les
nombres et les quatre opérations. Elle tournera sur le chunk qu'on a écrit à
la main au chapitre 9, celui de `-(1.2 + 3.4) / 5.6`.

Crée `mini_vm.c` à côté de `essai_chunk.c`. On commence par ce que la VM doit
retenir :

```c fichier="mini_vm.c"
// Une première VM : une pile, un ip, et un switch.
#include <stdio.h>
#include "chunk.h"

#define PILE_MAX 256

typedef struct{
    Chunk *chunk;
    uint8_t *ip;            // le prochain octet à lire
    Value pile[PILE_MAX];
    Value *sommet;          // la première case libre
}MiniVM;

static void push(MiniVM *vm, Value v){ *vm->sommet++ = v; }
static Value pop(MiniVM *vm){ return *--vm->sommet; }
```

Trois choses suffisent. Le chunk qu'on exécute. `ip`, le pointeur
d'instruction : l'adresse du prochain octet à lire. On aurait pu garder un
indice (`int offset`) et écrire `chunk->code[offset]`, mais un pointeur évite
une addition à chaque octet lu, et c'est ce que font toutes les VM écrites en
C, de CPython à Lua. Et la pile, avec `sommet` qui pointe sur la **première
case libre**, pas sur la dernière occupée.

Ce dernier choix décide de l'écriture de `push` et `pop`. `*vm->sommet++ = v`
écrit dans la case libre, puis avance. `*--vm->sommet` recule d'abord sur la
dernière case occupée, puis la lit. La pile vide, c'est `sommet == pile`, sans
cas particulier. Avec un `sommet` qui pointerait sur la dernière case occupée,
la pile vide demanderait un pointeur *avant* le tableau, ce que le C n'aime
pas.

Remarque aussi ce que `pop` ne fait pas : il n'efface rien. La valeur reste
dans la case, et sera écrasée par le prochain `push`. Effacer coûterait une
écriture pour rien.

Maintenant la boucle. Ajoute-la sous `pop` :

```c fichier="mini_vm.c"
static Value run(MiniVM *vm){
    #define READ_BYTE() (*vm->ip++)
    #define READ_SHORT() (vm->ip += 2,(uint16_t)((vm->ip[-2] << 8) | vm->ip[-1]))
    #define BINARY(op) do{ double b = AS_NUMBER(pop(vm)); double a = AS_NUMBER(pop(vm)); \
                           push(vm,NUMBER_VAL(a op b)); }while(0)
    for(;;){
        affiche_pile(vm);
        chunk_disassemble_instruction(vm->chunk,(int)(vm->ip - vm->chunk->code));
        switch(READ_BYTE()){
            case OP_CONSTANT: push(vm,vm->chunk->constants.values[READ_SHORT()]); break;
            case OP_ADD:      BINARY(+); break;
            case OP_SUBTRACT: BINARY(-); break;
            case OP_MULTIPLY: BINARY(*); break;
            case OP_DIVIDE:   BINARY(/); break;
            case OP_NEGATE:   push(vm,NUMBER_VAL(-AS_NUMBER(pop(vm)))); break;
            case OP_RETURN:   return pop(vm);
            default:
                printf("instruction inconnue\n");
                return NONE_VAL;
        }
    }
    #undef READ_BYTE
    #undef READ_SHORT
    #undef BINARY
}
```

C'est toute la machine virtuelle. Lire un octet, choisir, faire, recommencer.
On appelle ça la boucle de **dispatch** (d'aiguillage), et toutes les VM du
monde ont la même au fond.

Trois lignes méritent qu'on s'arrête.

`READ_SHORT` avance `ip` de deux octets d'un coup, *puis* relit les deux
octets qu'il vient de dépasser (`ip[-2]` et `ip[-1]`). Pourquoi pas
`(READ_BYTE() << 8) | READ_BYTE()` ? Parce qu'en C, l'ordre dans lequel les
deux côtés d'un `|` sont calculés n'est pas fixé. Le compilateur a le droit de
lire l'octet de poids faible en premier, et on obtiendrait 256 fois la bonne
valeur, une fois sur deux selon le compilateur. L'opérateur virgule, lui,
garantit l'ordre.

`BINARY` dépile `b` **avant** `a`. Le compilateur a poussé le côté gauche en
premier : il est donc sous le côté droit. Inverser ces deux lignes donnerait
`5.6 / 4.6` au lieu de `4.6 / 5.6`. C'est le bug le plus classique d'une
première VM, et il ne se voit pas avec `+` ni `*`.

`do{ ... }while(0)` autour de la macro permet de l'écrire comme une
instruction, suivie d'un `;`, même dans un `if` sans accolades. C'est l'idiome
habituel du C pour une macro de plusieurs instructions.

Il reste `affiche_pile`, qui sert à voir la machine travailler, et le `main`,
qui fabrique le chunk du chapitre 9 :

```c fichier="mini_vm.c"
static void affiche_pile(MiniVM *vm){
    printf("          ");
    if(vm->sommet == vm->pile)
        printf("(vide)");
    for(Value *v = vm->pile; v < vm->sommet; v++)
        printf("[ %g ]",AS_NUMBER(*v));
    printf("\n");
}

static void emet_constante(Chunk *chunk, double x){
    int k = chunk_add_constant(chunk,NUMBER_VAL(x));
    chunk_write(chunk,OP_CONSTANT,NULL);
    chunk_write(chunk,(uint8_t)(k >> 8),NULL);
    chunk_write(chunk,(uint8_t)k,NULL);
}

int main(void){
    Chunk chunk;
    chunk_init(&chunk);
    emet_constante(&chunk,1.2);
    emet_constante(&chunk,3.4);
    chunk_write(&chunk,OP_ADD,NULL);
    emet_constante(&chunk,5.6);
    chunk_write(&chunk,OP_DIVIDE,NULL);
    chunk_write(&chunk,OP_NEGATE,NULL);
    chunk_write(&chunk,OP_RETURN,NULL);

    MiniVM vm = {.chunk = &chunk,.ip = chunk.code};
    vm.sommet = vm.pile;
    Value resultat = run(&vm);
    printf("résultat : %g\n",AS_NUMBER(resultat));
    chunk_free(&chunk);
    return 0;
}
```

(Dans le fichier, `affiche_pile` est placée avant `run`, puisque `run`
l'appelle.) On compile avec les mêmes fichiers qu'au chapitre 9 :

Chaque instruction est affichée avec, au-dessus, la pile telle qu'elle la
trouve. On voit le `ADD` remplacer deux cases par une, le `NEGATE` changer la
case du sommet sur place. Les lignes valent 0 parce qu'on a passé `NULL` comme
noeud : il n'y a pas de programme source derrière ce chunk.

Garde ce fichier. Tout le reste du chapitre consiste à faire grandir cette
boucle jusqu'à `vm_run`, dans `src/vm/vm.c`, et à chaque étape on garde la
même forme : lire, choisir, faire.

> [!note]
> Afficher la pile avant chaque instruction est la première chose qu'on
> écrit dans une VM, et la dernière qu'on enlève. *Crafting Interpreters*
> l'active avec une option de compilation (`DEBUG_TRACE_EXECUTION`). Dans
> CeFlo, `--dis` montre le code mais pas la pile : c'est l'un des défis de fin
> de chapitre.

## 11.2 La vraie VM et sa pile

La mini VM a deux défauts qui la rendent inutilisable pour CeFlo. Elle
n'exécute qu'un chunk, alors qu'un programme en a un par fonction. Et sa pile
fait 256 cases, alors que `fib(30)` empile des milliers de valeurs. Voici la
structure qui la remplace, dans `src/vm/vm.h` :

```c fichier="src/vm/vm.h" lignes="22-45"
    // Autant d'appels imbriqués que l'ancien interpréteur. La pile est réservée
    // une fois (64 Mo) : le système ne donne la mémoire qu'aux pages touchées.
    #define FRAMES_MAX 100000
    #define STACK_MAX (1 << 22)

    typedef struct{
        ObjClosure *closure;
        uint8_t *ip;
        Value *slots;
    }CallFrame;

    typedef struct VM{
        CallFrame *frames;          // FRAMES_MAX cases, allouées par vm_init
        int frame_count;

        Value *stack;               // STACK_MAX cases
        Value *stack_top;

        ObjUpvalue *open_upvalues;  // les variables capturées encore sur la pile

        Table strings;              // toutes les chaînes internées (le GC les retire)
        Table builtins;             // println, print, input, argv... visibles partout
        Table modules;              // chemin -> ObjModule : un fichier ne s'exécute qu'une fois
        Table native_modules;       // `os`, `console` : nom -> ObjModule déjà rempli
```

`stack` et `stack_top` sont la pile de la mini VM, en plus grand : 4 194 304
cases (`1 << 22`) de 16 octets, soit 64 Mo. Ça paraît énorme, et ça le serait
si on touchait tout. Mais `vm_init` réserve ce tableau avec un seul `malloc`,
et un système comme Linux ne donne vraiment la mémoire qu'aux pages qu'on
écrit. Un script qui n'utilise que cent cases ne coûte que quelques kilo-octets.

Pourquoi une pile de taille fixe, et pas un tableau qui grandit ? À cause des
pointeurs. `CallFrame.slots` pointe dans la pile, les upvalues du chapitre 12
aussi. Si on agrandissait la pile avec `realloc`, elle pourrait changer
d'adresse, et tous ces pointeurs deviendraient faux d'un coup. Lua agrandit
sa pile, mais doit alors corriger chaque pointeur qui y mène
(`luaD_reallocstack`). CeFlo réserve une fois pour toutes, et c'est fini.

`frames` est le nouveau venu. Il y a un `CallFrame` par appel de fonction en
cours, et on en parlera en détail en 11.5. Pour l'instant, retiens qu'un cadre
garde la closure qui tourne, son propre `ip`, et `slots`, l'adresse de sa case
0 dans la pile.

Les quatre tables, enfin. `strings` sert à l'internement des chaînes (11.9),
`builtins` aux `println` et compagnie, `modules` et `native_modules` aux
`import` du chapitre 14. La suite de la structure est le GC (11.8).

Les opérations de pile sont dans le même en-tête, et ce sont exactement
celles de la mini VM :

```c fichier="src/vm/vm.h" lignes="86-88"
    static inline void vm_push(VM *vm, Value value){ *vm->stack_top++ = value; }
    static inline Value vm_pop(VM *vm){ return *--vm->stack_top; }
    static inline Value vm_peek(VM *vm, int distance){ return vm->stack_top[-1 - distance]; }
```

`static inline` dans un en-tête : chaque fichier qui l'inclut a sa copie, que
le compilateur C remplace par les deux instructions machine qu'elle contient.
Pas d'appel de fonction pour pousser une valeur. `vm_peek(vm, 0)` lit le
sommet sans le retirer, `vm_peek(vm, 1)` la case en dessous.

Il n'y a aucune vérification de débordement dans `vm_push`. La pile ne
déborde que si un appel de fonction la remplit, et c'est à l'entrée de
l'appel qu'on vérifie qu'il reste de la place (11.5). Tester à chaque `push`
coûterait un test par instruction, pour un cas qui n'arrive qu'en cas de
récursion infinie.

### Où se trouve la VM

La VM est une seule variable, déclarée dans `src/vm/main.c` :

```c fichier="src/vm/main.c" lignes="21-22"
// La VM est grande (ses CallFrame) : elle ne tient pas sur la pile C.
static VM vm;
```

Elle n'est pas globale pour autant : toutes les fonctions de la VM la
reçoivent en premier argument (`VM *vm`). C'est un choix qu'on retrouve dans
Lua (`lua_State *L`) : rien n'empêcherait de créer deux VM dans le même
programme, et le code dit toujours explicitement quelle VM il touche.

## 11.3 Des variables locales du C

On peut maintenant écrire le début de `vm_run`. Dans `src/vm/vm.c`, la boucle
commence par cinq variables et une macro :

```c fichier="src/vm/vm.c" lignes="622-644"
static Value vm_run(VM *vm, int base){
    CallFrame *frame;
    uint8_t *ip;
    Value *slots;
    Value *constants;
    ObjModule *module;

    #define LOAD_FRAME() do{                                            \
        frame = &vm->frames[vm->frame_count - 1];                       \
        ip = frame->ip;                                                 \
        slots = frame->slots;                                           \
        constants = frame->closure->function->chunk.constants.values;   \
        module = frame->closure->function->module;                      \
    }while(0)

    #define SYNC() (frame->ip = ip)
    #define READ_BYTE() (*ip++)
    #define READ_SHORT() (ip += 2,(uint16_t)((ip[-2] << 8) | ip[-1]))
    #define READ_CONSTANT() (constants[READ_SHORT()])
    #define READ_STRING() AS_STRING(READ_CONSTANT())
    #define PUSH(v) vm_push(vm,(v))
    #define POP() vm_pop(vm)
    #define PEEK(n) (vm->stack_top[-1 - (n)])
```

Compare avec la mini VM. Elle écrivait `vm->ip`, ici on écrit `ip`. Elle
lisait `vm->chunk->constants.values[k]`, ici `constants[k]`. Ce n'est pas une
question de style.

`vm->ip` est un champ d'une structure en mémoire. Chaque `READ_BYTE()` le
lirait, l'augmenterait et le réécrirait en mémoire, parce que le compilateur C
ne peut pas prouver qu'aucune fonction appelée ne le modifie entre deux
lectures. Une variable locale, dont personne ne prend l'adresse, peut vivre
dans un **registre** du processeur tout au long de la boucle. `ip`, `slots` et
`constants` sont lus à chaque instruction ou presque : les garder en
registres est le plus gros gain de la boucle après le choix du bytecode
lui-même. CPython fait exactement pareil dans `ceval.c`, avec ses variables
`next_instr` et `stack_pointer`.

Le prix, c'est que la VM a désormais deux copies de la position : `ip` dans un
registre, et `frame->ip` dans le cadre. `LOAD_FRAME` copie du cadre vers les
registres, quand on change de fonction. `SYNC` copie dans l'autre sens, et on
verra en 11.6 qu'oublier un `SYNC` donne des erreurs à la mauvaise ligne.

`base` est le nombre de cadres qui existaient avant cet appel de `vm_run`. On
en a besoin parce que `vm_run` peut être appelée pendant qu'une autre
`vm_run` tourne déjà (11.7). `CALLED` sert après un appel de fonction (11.5).

### Les premières instructions

La boucle elle-même commence, dans sa version `switch`, comme celle de la mini
VM :

```c fichier="src/vm/vm.c" lignes="694-712"
    LOAD_FRAME();

#ifdef USE_COMPUTED_GOTO
    NEXT();
    {
#else
    next:
    switch(READ_BYTE()){
#endif

    // ======== valeurs ========

    CASE(OP_CONSTANT): PUSH(READ_CONSTANT()); NEXT();
    CASE(OP_NONE): PUSH(NONE_VAL); NEXT();
    CASE(OP_TRUE): PUSH(BOOL_VAL(true)); NEXT();
    CASE(OP_FALSE): PUSH(BOOL_VAL(false)); NEXT();
    CASE(OP_POP): vm->stack_top--; NEXT();
    CASE(OP_DUP): PUSH(PEEK(0)); NEXT();
    CASE(OP_DUP2): PUSH(PEEK(1)); PUSH(PEEK(1)); NEXT();
```

Oublie un instant le `#ifdef` : on le comprendra en 11.10. Sans lui, `CASE(op)`
vaut `case op` et `NEXT()` vaut `goto next`, un saut au début du `switch`. Ce
sont les `case` de la mini VM, écrits avec des macros pour pouvoir changer de
méthode d'aiguillage plus tard sans toucher aux soixante-cinq instructions.

`OP_POP` ne lit même pas la valeur : il recule `stack_top`. `OP_DUP2` pousse
deux fois `PEEK(1)` : la première fois, `PEEK(1)` est `a` (sous `b`) ; après
ce `PUSH`, la pile est `a b a`, et `PEEK(1)` est maintenant `b`. Deux lignes
identiques qui ne lisent pas la même case : c'est le genre de chose qu'on
vérifie en dessinant la pile.

```text
DUP2      pile : a b
PUSH(PEEK(1))   : a b a
PUSH(PEEK(1))   : a b a b
```

### Les variables

```c fichier="src/vm/vm.c" lignes="716-751"
    CASE(OP_GET_LOCAL): PUSH(slots[READ_BYTE()]); NEXT();
    CASE(OP_SET_LOCAL): slots[READ_BYTE()] = PEEK(0); NEXT();
    CASE(OP_GET_UPVALUE): PUSH(*frame->closure->upvalues[READ_BYTE()]->location); NEXT();
    CASE(OP_SET_UPVALUE): *frame->closure->upvalues[READ_BYTE()]->location = PEEK(0); NEXT();

    CASE(OP_GET_GLOBAL):{
        int index = READ_SHORT();
        Value value = module->globals.values[index];
        if(IS_UNDEFINED(value)){
            SYNC();
            value = undefined_global(vm,module,index);
        }
        PUSH(value);
        NEXT();
    }
    CASE(OP_SET_GLOBAL):{
        int index = READ_SHORT();
        SYNC();
        set_global(vm,module,index,PEEK(0));
        NEXT();
    }
    CASE(OP_DEFINE_GLOBAL):{
        int index = READ_SHORT();
        module->globals.values[index] = POP();
        NEXT();
    }
    CASE(OP_GET_BUILTIN):{
        ObjString *name = READ_STRING();
        Value value;
        if(!table_get(&vm->builtins,name,&value)){
            SYNC();
            vm_error(vm,"`%s` n'est pas définie",name->chars);
        }
        PUSH(value);
        NEXT();
    }
```

Voilà, en une ligne, ce que tout le chapitre 10 a préparé. `GET_LOCAL` est un
accès à un tableau : `slots[1]`. Il n'y a pas de nom, pas de hash, pas de
`strcmp`. Le visitor faisait cinq recherches par tour de la boucle de 9.2 ;
la VM fait cinq lectures de tableau.

`GET_GLOBAL` est presque aussi simple : la case `index` du tableau des
globales du module. Le seul test, `IS_UNDEFINED`, attrape les deux cas qu'on a
vus en 10.4 : une globale pas encore définie (l'erreur « n'est pas définie »)
ou un fichier qui définit plus bas son propre `println` (on rend le builtin).
Les deux sont rares, et ils partent dans `undefined_global`, une fonction à
part :

```c fichier="src/vm/vm.c" lignes="523-529" fonction="undefined_global"
// OP_GET_GLOBAL d'une globale pas encore définie : un builtin du même nom, sinon une erreur.
static Value undefined_global(VM *vm, ObjModule *module, int index){
    Value value;
    if(table_get(&vm->builtins,module->names[index],&value))
        return value;
    vm_error(vm,"`%s` n'est pas définie",module->names[index]->chars);
}
```

C'est une règle qu'on suit dans tout `vm_run` : le cas fréquent reste dans le
`case`, en quelques lignes ; le cas rare, l'erreur, le travail lent, vont dans
une fonction. Une boucle courte tient mieux dans le cache d'instructions du
processeur, et le compilateur C optimise mieux une fonction de taille
raisonnable qu'un `switch` de deux mille lignes.

`DEFINE_GLOBAL` ne vérifie rien : le compilateur a déjà refusé les
redéfinitions interdites. `SET_GLOBAL` passe par `set_global`, qui vérifie
que la globale existe, qu'elle n'est pas constante, et son type.

`GET_BUILTIN`, lui, cherche vraiment un nom dans une table de hachage. C'est
la seule recherche par nom de la boucle, et elle est rapide : le nom est une
chaîne internée (son hash est déjà calculé, la comparaison se fait par
adresse), et un programme appelle `println` beaucoup moins souvent qu'il ne
lit `i`.

## 11.4 Les opérateurs et les sauts

Dans la mini VM, `BINARY` supposait que tout était un nombre. CeFlo a des
règles plus riches : `"a" + 1` donne `"a1"`, `[1] + [2]` concatène, `"ab" * 3`
répète. Les nombres restent pourtant le cas qui compte, celui des boucles.
La VM traite donc deux nombres tout de suite, et confie le reste à
`vm_binary` :

```c fichier="src/vm/vm.c" lignes="649-663"
    // Deux nombres : le cas rapide. Le reste suit vm_binary.
    #define BINARY(op,result) do{                                       \
        Value b = PEEK(0), a = PEEK(1);                                 \
        if(IS_NUMBER(a) && IS_NUMBER(b)){                               \
            vm->stack_top -= 1;                                         \
            vm->stack_top[-1] = result;                                 \
        }else{                                                          \
            SYNC();                                                     \
            Value r = vm_binary(vm,op,a,b);                             \
            vm->stack_top -= 1;                                         \
            vm->stack_top[-1] = r;                                      \
        }                                                               \
    }while(0)
    #define NUM_A AS_NUMBER(a)
    #define NUM_B AS_NUMBER(b)
```

Deux différences avec la mini VM. D'abord `PEEK` au lieu de `POP` : on lit `a`
et `b` sans les retirer, puis on retire une seule case et on écrit le résultat
dans l'autre. Une écriture de moins qu'un `POP`, `POP`, `PUSH`.

Ensuite, et c'est plus subtil, `a` et `b` restent sur la pile pendant
`vm_binary`. `"a" + objet` doit appeler le `__str__` de l'objet, donc du code
CeFlo, qui peut déclencher le GC. Si `a` et `b` avaient déjà quitté la pile,
le GC ne les verrait plus et pourrait libérer la chaîne `"a"` au milieu de la
concaténation. On reviendra sur cette règle en 11.8 ; retiens qu'en laissant
les valeurs sur la pile, on ne pense plus à les protéger.

Les instructions s'écrivent alors en une ligne chacune :

```c fichier="src/vm/vm.c" lignes="768-774"
    CASE(OP_ADD): BINARY(OP_ADD,NUMBER_VAL(NUM_A + NUM_B)); NEXT();
    CASE(OP_SUBTRACT): BINARY(OP_SUBTRACT,NUMBER_VAL(NUM_A - NUM_B)); NEXT();
    CASE(OP_MULTIPLY): BINARY(OP_MULTIPLY,NUMBER_VAL(NUM_A * NUM_B)); NEXT();
    CASE(OP_LESS): BINARY(OP_LESS,BOOL_VAL(NUM_A < NUM_B)); NEXT();
    CASE(OP_LESS_EQUAL): BINARY(OP_LESS_EQUAL,BOOL_VAL(NUM_A <= NUM_B)); NEXT();
    CASE(OP_GREATER): BINARY(OP_GREATER,BOOL_VAL(NUM_A > NUM_B)); NEXT();
    CASE(OP_GREATER_EQUAL): BINARY(OP_GREATER_EQUAL,BOOL_VAL(NUM_A >= NUM_B)); NEXT();
```

`NUM_A` et `NUM_B` ne sont que des raccourcis pour `AS_NUMBER(a)` et
`AS_NUMBER(b)`, les deux variables déclarées à l'intérieur de `BINARY`. Une
macro qui utilise des noms déclarés par une autre macro, c'est fragile, mais
ça rend chaque ligne lisible d'un coup d'oeil.

La division a un cas de plus : diviser par zéro est une erreur en CeFlo, pas
un infini comme en C.

```c fichier="src/vm/vm.c" lignes="776-788"
    // Une division par zéro passe par vm_binary, qui affiche l'erreur.
    CASE(OP_DIVIDE):
        if(IS_NUMBER(PEEK(0)) && AS_NUMBER(PEEK(0)) == 0)
            goto divide_slow;
        BINARY(OP_DIVIDE,NUMBER_VAL(NUM_A / NUM_B));
        NEXT();
    divide_slow:{
        SYNC();
        Value r = vm_binary(vm,OP_DIVIDE,PEEK(1),PEEK(0));
        vm->stack_top -= 1;
        vm->stack_top[-1] = r;
        NEXT();
    }
```

Plutôt que d'écrire le message ici, on envoie le cas zéro vers `vm_binary`,
qui connaît déjà tous les messages (`src/vm/binary.c`). Les règles de CeFlo
sur les opérateurs restent ainsi à un seul endroit.

`vm_binary` est la traduction de `value_expr` du chapitre 5, pour les
nouvelles valeurs. Son début dit tout de sa logique :

```c fichier="src/vm/binary.c" lignes="195-219" fonction="vm_binary"
Value vm_binary(VM *vm, OpCode op, Value a, Value b){
    switch(op){
        case OP_EQUAL: return BOOL_VAL(value_equals(a,b));
        case OP_NOT_EQUAL: return BOOL_VAL(!value_equals(a,b));
        case OP_LESS:
        case OP_LESS_EQUAL:
        case OP_GREATER:
        case OP_GREATER_EQUAL:
            return binary_compare(vm,op,a,b);
        case OP_ADD:
            if(IS_STRING(a) || IS_STRING(b))
                return binary_concat(vm,a,b);
            if(IS_LIST(a) && IS_LIST(b))
                return binary_list_concat(vm,AS_LIST(a),AS_LIST(b));
            break;
        case OP_MULTIPLY:
            if(IS_STRING(a) && IS_NUMBER(b))
                return binary_repeat(vm,AS_STRING(a),AS_NUMBER(b));
            break;
        default:
            break;
    }

    if(!binary_is_numeric(a) || !binary_is_numeric(b))
        binary_error(vm,op,a,b);
```

D'abord les cas qui ne sont pas des calculs : comparer, concaténer, répéter.
Ensuite, un `bool` ou un `char` comptent comme des nombres (`true + 1` vaut 2,
comme dans le visitor), et le reste est une erreur avec les deux types dans le
message.

### Les sauts

```c fichier="src/vm/vm.c" lignes="829-848"
    CASE(OP_JUMP):{
        int distance = READ_SHORT();
        ip += distance;
        NEXT();
    }
    CASE(OP_JUMP_IF_FALSE):{
        int distance = READ_SHORT();
        Value condition = POP();
        bool truth = IS_BOOL(condition) ? AS_BOOL(condition) : value_is_true(condition);
        if(!truth)
            ip += distance;
        NEXT();
    }
    CASE(OP_LOOP):{
        int distance = READ_SHORT();
        ip -= distance;
        SYNC();
        SAFEPOINT();
        NEXT();
    }
```

Un saut est une addition sur `ip`. On lit l'opérande d'abord, ce qui place
`ip` juste après l'instruction : c'est pour ça que le compilateur comptait les
distances « depuis l'octet qui suit ».

`JUMP_IF_FALSE` a son propre petit raccourci. Une condition est presque
toujours un booléen sorti d'une comparaison : on lit le booléen directement.
Sinon, `value_is_true` applique les règles de CeFlo (`0`, `""`, `none`, une
liste vide sont faux). Le test `IS_BOOL` coûte une comparaison et évite un
appel de fonction et un `switch` dans le cas courant.

`LOOP`, enfin, est un **point sûr** pour le GC : `SAFEPOINT()` peut lancer une
collecte. On verra en 11.8 pourquoi on choisit cet endroit, et pourquoi il
faut un `SYNC()` juste avant.

## 11.5 Appeler une fonction

Un appel de fonction est le moment le plus délicat d'une VM, et celui qui
compte le plus pour la vitesse : `fib(30)` en fait 2,7 millions. Reprends le
bytecode de `plus_un.cf` du chapitre 9 :

```text
GET_GLOBAL 0    pile : ... plus_un
CONSTANT 2      pile : ... plus_un 41
CALL 1          ?
```

Au moment du `CALL 1`, la fonction est sous son argument. Le compilateur de
`plus_un` a décidé que `a` serait la case 1, et il a réservé la case 0. Si on
fait commencer les cases de `plus_un` sur la case où se trouve la fonction
elle-même, tout tombe en place sans rien copier :

```text
                 slots de plus_un
                 |
pile :  ... println  plus_un  41
                     case 0   case 1 (a)
```

C'est l'idée qui rend les appels bon marché : **les arguments poussés par
l'appelant deviennent les paramètres de la fonction appelée**, à l'endroit où
ils sont. Un `CallFrame` dit simplement où commencent les cases de chaque
fonction en cours.

Voici l'instruction :

```c fichier="src/vm/vm.c" lignes="852-864"
    CASE(OP_CALL):{
        int argc = READ_BYTE();
        Value callee = PEEK(argc);
        SYNC();
        // Une closure est le cas fréquent : sans passer par call_value.
        if(IS_CLOSURE(callee)){
            call_closure(vm,AS_CLOSURE(callee),argc);
            CALLED(true);
        }else{
            CALLED(call_value(vm,callee,argc));
        }
        NEXT();
    }
```

La fonction appelée est `argc` cases sous le sommet : `PEEK(argc)`. On
synchronise `ip` d'abord, et c'est obligatoire ici : `call_closure` va créer
un nouveau cadre, et l'ancien doit savoir où reprendre au retour. Puis on
ouvre le cadre :

```c fichier="src/vm/vm.c" lignes="150-163" fonction="call_closure"
static void call_closure(VM *vm, ObjClosure *closure, int argc){
    ObjFunction *function = closure->function;
    if(argc != function->arity){
        vm_error(vm,"`%s` prend %d argument(s), mais en reçoit %d",
            function->name != NULL ? function->name->chars : "?",function->arity,argc);
    }
    if(vm->frame_count == FRAMES_MAX || vm->stack_top - vm->stack > STACK_MAX - 512)
        vm_error(vm,TOO_DEEP);

    CallFrame *frame = &vm->frames[vm->frame_count++];
    frame->closure = closure;
    frame->ip = function->chunk.code;
    frame->slots = vm->stack_top - argc - 1;
}
```

Ligne par ligne :

- le nombre d'arguments doit être exact. CeFlo n'a pas de paramètres
  facultatifs ;
- on vérifie qu'il reste un cadre libre, et au moins 512 cases de pile.
  Pourquoi 512 ? Une fonction utilise au plus 256 locales, plus quelques
  valeurs temporaires : 512 cases de marge garantissent que la fonction qui
  démarre ne débordera pas, sans tester chaque `push` ;
- on remplit le cadre : la closure, un `ip` au début de son code, et `slots`
  qui pointe sur la case de la fonction appelée, `argc + 1` cases sous le
  sommet.

Rien n'est copié. Rien n'est alloué. Un appel CeFlo, c'est trois écritures
dans un tableau de cadres préparé d'avance. Le visitor, lui, allouait une
portée (une table de hachage) à chaque appel, et y rangeait chaque paramètre
par son nom.

`CALLED(true)` termine le travail :

```c fichier="src/vm/vm.c" lignes="646-647"
    // Un appel ou un retour : on reprend la fonction qui est maintenant en haut.
    #define CALLED(opened) do{ if(opened){ LOAD_FRAME(); SAFEPOINT(); } }while(0)
```

`LOAD_FRAME` charge le nouveau cadre dans les registres : `ip` pointe
maintenant au début de `plus_un`, et la boucle continue, sans le savoir, dans
une autre fonction. Il n'y a pas d'appel C récursif : un appel CeFlo ne fait
pas grandir la pile du C. C'est ce qui permet `FRAMES_MAX`, 100 000 appels
imbriqués, là où le visitor, récursif en C, devait surveiller la pile du
système.

### Le retour

```c fichier="src/vm/vm.c" lignes="884-895"
    CASE(OP_RETURN):{
        Value result = POP();
        close_upvalues(vm,slots);
        vm->frame_count--;
        vm->stack_top = slots;
        if(vm->frame_count == base)
            return result;
        PUSH(result);
        LOAD_FRAME();
        SAFEPOINT();
        NEXT();
    }
```

On garde la valeur de retour, on ferme les upvalues (chapitre 12), on supprime
le cadre. Puis `vm->stack_top = slots` : la pile redescend d'un coup jusqu'à
la case 0 de la fonction. Les paramètres, les locales, et la fonction
elle-même disparaissent en une affectation. On pose le résultat à leur place,
et on recharge le cadre de l'appelant, dont l'`ip` (synchronisé avant le
`CALL`) pointe juste après le `CALL`.

Dessine `plus_un(41)` :

```text
avant CALL 1      : println plus_un 41
                            ^ slots
pendant plus_un   : println plus_un 41 1        (GET_LOCAL 1, CONSTANT 0)
                  : println plus_un 42          (ADD)
RETURN            : result = 42, stack_top = slots
                  : println 42
```

Exactement ce que promettait la trace de 9.4 : la fonction et ses arguments
sont remplacés par le résultat.

Le test `vm->frame_count == base` arrête `vm_run` quand la fonction qui l'a
lancée retourne. Pour le programme principal, `base` vaut 0 : le dernier
`RETURN` du fichier rend sa valeur au C. On verra en 11.7 pourquoi `base`
n'est pas toujours 0.

## 11.6 Les erreurs à la bonne ligne

On a écrit `SYNC()` une douzaine de fois sans vraiment l'expliquer. Voici
comment la VM trouve la ligne d'une erreur :

```c fichier="src/vm/vm.c" lignes="44-60"
static ast_t *frame_node(CallFrame *frame){
    Chunk *chunk = &frame->closure->function->chunk;
    int offset = (int)(frame->ip - chunk->code) - 1;
    return chunk->nodes[offset < 0 ? 0 : offset];
}

ast_t *vm_current_node(VM *vm){
    if(vm->frame_count == 0)
        return NULL;
    return frame_node(&vm->frames[vm->frame_count - 1]);
}

void vm_error(VM *vm, const char *format, ...){
    va_list args;
    va_start(args,format);
    error_node_v(vm_current_node(vm),format,args);
}
```

`vm_error` prend le cadre du sommet, lit son `ip`, recule d'un octet (`ip`
pointe déjà *après* l'octet en cours) et cherche le noeud de cet octet dans
`chunk->nodes`, le tableau du chapitre 9. `error_node_v` est la fonction
d'affichage de `src/error.c`, la même que celle du visitor : ligne, colonne,
flèche.

Tout repose sur `frame->ip`. Or pendant la boucle, la vraie position est dans
la variable `ip`, et `frame->ip` n'est mis à jour qu'aux `SYNC()`. Si on
oublie un `SYNC()` avant une instruction qui peut échouer, `vm_error` lit une
position périmée, celle du dernier `SYNC()`.

Pour le voir, j'ai fabriqué dans `build/` une copie de `vm.c` sans le `SYNC()`
de `divide_slow` (une ligne en moins, rien d'autre). Le programme
`division.cf` du chapitre 9 donne alors :

```terminal
$ ./Ceflo_nosync division.cf
x vaut 10
erreur: division par zéro
  --> division.cf:3:8
    3 | println("x vaut ", x)
      |        ^
```

La bonne erreur, au mauvais endroit : la ligne 3 est juste, sans reproche.
Le dernier `SYNC()` exécuté était celui du `CALL` de `println` à la ligne 3,
et la VM croit être encore là. Imagine chercher ce bug dans un programme de
mille lignes : le message t'envoie au mauvais endroit, et tu n'as aucune
raison de te méfier. C'est pour ça que la règle de `vm.c` est simple et
stricte : **avant tout ce qui peut afficher une erreur ou rappeler du CeFlo,
SYNC()**.

Pourquoi ne pas faire `SYNC()` à chaque instruction, pour être tranquille ?
Parce que c'est une écriture en mémoire de plus par instruction, sur le
chemin le plus chaud du programme. Le cas rapide de `BINARY` (deux nombres)
ne fait pas de `SYNC()`, et c'est voulu : il ne peut pas échouer.

### L'erreur chez l'appelant

Un paramètre mal typé est la faute de celui qui appelle. Au chapitre 10, on a
vu l'erreur de `moyenne(3, "4")` pointer sur l'appel, alors que le
`CHECK_TYPE` est dans `moyenne`. Voici comment :

```c fichier="src/vm/vm.c" lignes="68-73" fonction="caller_node"
// Un paramètre ou un retour faux se signale là où la fonction a été appelée.
static ast_t *caller_node(VM *vm){
    if(vm->frame_count >= 2)
        return frame_node(&vm->frames[vm->frame_count - 2]);
    return vm->frames[vm->frame_count - 1].closure->function->definition;
}
```

On lit le cadre *sous* le sommet, celui de l'appelant. Son `ip` a été
synchronisé par le `CALL` : il pointe juste après, et le noeud de l'octet
précédent est l'appel lui-même. C'est le bénéfice discret d'avoir un cadre par
appel : la pile des cadres est aussi la pile des endroits où chaque fonction
attend, et on pourrait afficher toute la chaîne des appels (c'est l'un des
défis).

## 11.7 Les natives, et la VM qui se rappelle elle-même

`println` n'est pas une closure : c'est une fonction C. Toutes les fonctions
C appelables depuis CeFlo ont la même forme, déclarée dans `object.h` :

```c fichier="src/vm/object.h" lignes="219-227"
    // Une fonction C. Elle reçoit ses arguments et retourne sa valeur.
    // Une erreur s'écrit vm_error(vm, ...) : le programme s'arrête.
    typedef Value (*NativeFn)(struct VM *vm, int argc, Value *args);

    typedef struct{
        Obj obj;
        NativeFn function;
        const char *name;   // un texte qui vit jusqu'à la fin du programme
    }ObjNative;
```

Une native reçoit la VM, le nombre d'arguments, et un pointeur sur le premier
argument. Ce pointeur pointe **dans la pile** : la native lit ses arguments
là où le bytecode les a poussés, sans copie. Voici `println`, dans
`src/vm/natives/core.c` :

```c fichier="src/vm/natives/core.c" lignes="23-33"
static Value core_print(VM *vm, int argc, Value *args){
    for(int i = 0; i < argc; i++)
        core_write(vm,stdout,args[i]);
    return NONE_VAL;
}

static Value core_println(VM *vm, int argc, Value *args){
    core_print(vm,argc,args);
    fputc('\n',stdout);
    return NONE_VAL;
}
```

Et voici comment elle est appelée, dans `call_value`, le chemin de tout ce qui
n'est pas une closure :

```c fichier="src/vm/vm.c" lignes="165-192" fonction="call_value"
/*
    La pile contient [case0 a1..an]. Appelle `callee` : une closure ouvre un
    nouveau CallFrame (retourne true), une native s'exécute tout de suite et
    laisse son résultat à la place de case0 (retourne false).
*/
static bool call_value(VM *vm, Value callee, int argc){
    if(IS_OBJ(callee)){
        switch(OBJ_TYPE(callee)){
            case OBJ_CLOSURE:
                call_closure(vm,AS_CLOSURE(callee),argc);
                return true;
            case OBJ_NATIVE:{
                Value result = AS_NATIVE(callee)->function(vm,argc,vm->stack_top - argc);
                vm->stack_top -= argc + 1;
                vm_push(vm,result);
                return false;
            }
            case OBJ_BOUND_METHOD:{
                ObjBoundMethod *bound = AS_BOUND_METHOD(callee);
                vm->stack_top[-argc - 1] = bound->receiver;
                return call_value(vm,bound->method,argc);
            }
            default:
                break;
        }
    }
    vm_error(vm,"%s n'est pas une fonction",value_type_name(callee));
}
```

La native s'exécute tout de suite, comme un appel C ordinaire, et son
résultat remplace la fonction et les arguments, comme un `RETURN`. Pas de
cadre. La valeur de retour, `false`, dit à `CALLED` qu'il n'y a pas de
nouveau cadre à charger.

Le troisième cas, la méthode liée (`p.avance` sans parenthèses, rangé dans une
variable), remplace la case 0 par l'objet et appelle la méthode : `self` se
retrouve en case 0, là où une méthode l'attend. Le chapitre 13 y revient.

Une native s'ajoute aux builtins avec `vm_define_builtin`, et `core.c` les
déclare toutes dans un tableau :

```c fichier="src/vm/natives/core.c" lignes="160-173"
static const core_function Core_List[] = {
    {"println",&core_println},
    {"print",&core_print},
    {"input",&core_input},
    {"format",&core_format},
    {"printf",&core_printf},
    {"nextInt",&core_nextInt},
    {"exit",&core_exit},
    {NULL,NULL}
};

void natives_define_core(VM *vm, int argc, char **argv){
    for(const core_function *item = Core_List; item->name != NULL; item++)
        vm_define_builtin(vm,item->name,item->function);
```

### Quand une native appelle du CeFlo

Certaines natives doivent appeler du code CeFlo. `liste.filter(f)` appelle `f`
sur chaque élément ; `println(objet)` appelle son `__str__`. La native est du
C, en plein milieu d'une instruction `CALL` de `vm_run`. Comment lance-t-elle
une fonction CeFlo et attend-elle son résultat ?

En relançant `vm_run`. C'est le rôle de `vm_call` :

```c fichier="src/vm/vm.c" lignes="196-214"
// Appelle `function` avec `first` en case 0 (self, ou la fonction elle-même).
static Value call_from_c(VM *vm, Value first, Value function, int argc, Value *args){
    if(ceflo_stack_exceeded())
        vm_error(vm,TOO_DEEP);

    Value *top = vm->stack_top;
    vm_push(vm,first);
    for(int i = 0; i < argc; i++)
        vm_push(vm,args[i]);

    int base = vm->frame_count;
    Value result = call_value(vm,function,argc) ? vm_run(vm,base) : vm_pop(vm);
    vm->stack_top = top;
    return result;
}

Value vm_call(VM *vm, Value function, int argc, Value *args){
    return call_from_c(vm,function,function,argc,args);
}
```

On pousse la fonction et ses arguments au sommet de la pile, au-dessus de
tout ce qui s'y trouve, comme le ferait un `CALL`. On note le nombre de
cadres actuel dans `base`. `call_value` ouvre le cadre de la fonction, et on
lance une **deuxième** `vm_run`, imbriquée dans la première. Celle-ci exécute
la fonction, et quand son `RETURN` ramène `frame_count` à `base`, elle s'arrête
et rend le résultat. C'est le test qu'on a vu dans `OP_RETURN`.

```text
vm_run (base 0)            le programme
  OP_INVOKE filter
    method_list_filter     du C
      vm_call(f, x)
        vm_run (base 3)    le corps de f
          OP_RETURN        frame_count revient à 3 : on rend la main au C
```

Ici, l'appel C grandit bel et bien, et c'est pour ça que `call_from_c`
commence par `ceflo_stack_exceeded()`, le même garde-fou que le visitor : un
`__str__` qui s'afficherait lui-même sans fin ferait déborder la pile du C.

Le reste de la VM appelle toujours `vm_call` pour lancer du CeFlo depuis le C,
et le programme principal lui-même ne fait pas autrement. Dans
`src/vm/module.c` :

```c fichier="src/vm/module.c" lignes="36-51" fonction="run_source"
// Analyse, compile et exécute un fichier. Le module est rangé avant l'exécution.
static ObjModule *run_source(VM *vm, lexer_t *lexer){
    ast_t *program = parser_parse(lexer);

    ObjModule *module = module_new(vm,string_from(vm,lexer->fileName));
    table_set(&vm->modules,module->path,OBJ_VAL(module));

    ObjFunction *function = compile_module(vm,program,module);
    if(vm->disassemble)
        disassemble_function(function);

    Value closure = OBJ_VAL(closure_new(vm,function));
    vm_call(vm,closure,0,NULL);
    module->loaded = true;
    return module;
}
```

Tout le chemin du livre tient dans ces lignes : le parser (chapitre 3),
le module et ses globales, le compilateur (chapitre 10), le désassembleur
(chapitre 9), et `vm_call` qui lance la boucle. Le fichier est une fonction
sans argument, et l'exécuter, c'est l'appeler.

## 11.8 Le GC aux points sûrs

Le chapitre 8 a raconté la grande difficulté d'un garbage collector : savoir
quelles valeurs sont encore utilisées à l'instant où il se déclenche. Le
visitor gardait une pile de temporaires qu'il fallait remplir et vider avec
soin, parce que le GC pouvait partir à n'importe quelle allocation. Chaque
oubli était un objet libéré trop tôt.

La VM prend le problème à l'envers. Le commentaire de `memory.h` l'annonce en
majuscules :

```c fichier="src/vm/memory.h" lignes="14-22"
 *      LA RÈGLE QUI REND TOUT SIMPLE : le GC ne se déclenche jamais pendant
 *      une allocation. Il ne tourne qu'aux points sûrs de la VM (gc_safepoint) :
 *      un appel, un retour, le tour d'une boucle. À ces moments-là, toutes les
 *      valeurs vivantes sont sur la pile de la VM.
 *
 *      Le compilateur et les natives peuvent donc allouer autant qu'ils veulent
 *      sans rien protéger. La seule exception : une native qui appelle
 *      vm_call, car le code CeFlo appelé passe par des points sûrs. Elle
 *      protège ses valeurs avec vm_protect (vm.h) ou en les posant sur la pile.
```

Regarde l'allocation, dans `src/vm/memory.c` :

```c fichier="src/vm/memory.c" lignes="46-57" fonction="vm_allocate_object"
Obj *vm_allocate_object(VM *vm, size_t size, ObjType type){
    pool_t *pool = memory_pool(size);
    Obj *object = pool != NULL ? pool_alloc(pool,memory_pool_size(size)) : ceflo_realloc(NULL,size);
    vm->bytes_allocated += size;

    object->type = type;
    object->marked = false;
    object->printing = false;
    object->next = vm->objects;
    vm->objects = object;
    return object;
}
```

Elle compte les octets, chaîne l'objet dans la liste du GC, et c'est tout.
Elle ne lance jamais de collecte. La collecte n'a lieu qu'ici :

```c fichier="src/vm/vm.c" lignes="612-616"
#ifdef CEFLO_GC_STRESS
    #define SAFEPOINT() gc_safepoint(vm)
#else
    #define SAFEPOINT() do{ if(vm->bytes_allocated > vm->next_gc) gc_safepoint(vm); }while(0)
#endif
```

Et `SAFEPOINT()` n'apparaît qu'à trois endroits de `vm_run` : après un appel
(`CALLED`), après un retour, et dans `OP_LOOP`. Pourquoi ces trois-là ? Parce
qu'à ces instants, entre deux instructions, la VM ne tient aucune valeur dans
une variable C. Tout ce qui est vivant est sur la pile de la VM, dans les
globales d'un module, ou atteignable depuis eux. Les racines sont faciles à
énumérer :

```c fichier="src/vm/memory.c" lignes="294-312" fonction="gc_mark_roots"
static void gc_mark_roots(VM *vm){
    for(Value *slot = vm->stack; slot < vm->stack_top; slot++)
        gc_mark_value(vm,*slot);
    for(int i = 0; i < vm->frame_count; i++)
        gc_mark_object(vm,(Obj*)vm->frames[i].closure);
    for(ObjUpvalue *upvalue = vm->open_upvalues; upvalue != NULL; upvalue = upvalue->next)
        gc_mark_object(vm,(Obj*)upvalue);
    for(int i = 0; i < vm->root_count; i++)
        gc_mark_value(vm,*vm->roots[i]);

    gc_mark_table(vm,&vm->builtins);
    gc_mark_table(vm,&vm->modules);
    gc_mark_table(vm,&vm->native_modules);

    gc_mark_object(vm,(Obj*)vm->name_init);
    gc_mark_object(vm,(Obj*)vm->name_str);
    gc_mark_object(vm,(Obj*)vm->name_cast);
    gc_mark_object(vm,(Obj*)vm->name_main);
}
```

La pile, les closures des cadres, les upvalues ouvertes, les valeurs
protégées, les tables de la VM. Les globales ne sont pas dans la liste : elles
sont dans les modules, eux-mêmes dans `vm->modules`, et le marquage les
atteint en suivant les objets (`gc_blacken`, le même parcours en gris et noir
qu'au chapitre 8).

Pourquoi est-ce suffisant ? Une boucle sans fin doit passer par `LOOP`, une
récursion par `CALL`. Un programme ne peut donc pas allouer longtemps sans
passer par un point sûr. Et entre deux points sûrs, il alloue sans limite,
sans rien protéger : c'est le confort qu'on voulait.

Le `SYNC()` qui précède le `SAFEPOINT()` de `OP_LOOP` n'est pas demandé par
le GC, qui ne lit jamais `ip`. Il garde simplement `frame->ip` à jour une fois
par tour de boucle, pour presque rien : si un jour un point sûr affiche
quelque chose (une trace, une erreur), la position sera juste.

### L'exception, et le bug qu'elle évite

Une native qui rappelle du CeFlo traverse des points sûrs : le code CeFlo
appelé fait des appels, des boucles. Pendant ce temps, les valeurs que la
native garde dans ses variables C sont invisibles pour le GC. `filter` en est
l'exemple parfait :

```c fichier="src/vm/natives/methods.c" lignes="83-104" fonction="method_list_filter"
static Value method_list_filter(VM *vm, Value self, int argc, Value *args){
    native_check_args(vm,"filter",argc,1);

    // La fonction appelée passe par des points sûrs du GC : tout ce qu'on garde est protégé.
    Value function = args[0];
    Value result = OBJ_VAL(list_new(vm));
    Value item = NONE_VAL;
    vm_protect(vm,&self);
    vm_protect(vm,&function);
    vm_protect(vm,&result);
    vm_protect(vm,&item);

    // Taille relue à chaque tour : la fonction peut modifier la liste.
    for(int i = 0; i < AS_LIST(self)->count; i++){
        item = AS_LIST(self)->items[i];
        if(value_is_true(vm_call(vm,function,1,&item)))
            list_append(vm,AS_LIST(result),item);
    }

    vm_unprotect(vm,4);
    return result;
}
```

La liste `result` est neuve : rien d'autre ne pointe vers elle. Sans le
`vm_protect(vm,&result)`, un GC lancé pendant un `vm_call` la libérerait, et
le `list_append` suivant écrirait dans une mémoire rendue au système.

Ce bug ne se voit presque jamais : il faut qu'une collecte tombe exactement
pendant un `filter`, avec assez de mémoire allouée pour la déclencher. Pour le
débusquer, le `Makefile` a `make sanitize`, qui compile la VM avec
AddressSanitizer (`-fsanitize=address`) et `CEFLO_GC_STRESS`, une VM où
*chaque* point sûr lance une collecte. J'ai retiré la ligne
`vm_protect(vm,&result)` dans une copie de `methods.c`, compilé ainsi dans
`build/`, et lancé un `filter` dont la fonction fait un appel (un `CALL`,
donc un point sûr) :

```ceflo fichier="filtre.cf"
func pair(x){ return x % 2 == 0 }
var l = [1, 2, 3, 4, 5, 6]
var pairs = l.filter(lfunc(x){ return pair(x) })
println(pairs)
```

La pile est l'autre façon de protéger une valeur. `binary_concat`, qui doit
appeler le `__str__` d'un objet pour le coller à une chaîne, pose simplement

```c fichier="src/vm/binary.c" lignes="112-125" fonction="binary_concat"
// Dès qu'une chaîne est présente, `+` assemble le texte des deux valeurs.
static Value binary_concat(VM *vm, Value a, Value b){
    // Un __str__ peut tourner pendant l'affichage de a : b doit rester en vie.
    vm_push(vm,a);
    vm_push(vm,b);
    TextPart left, right;
    binary_text(vm,&left,&a);
    binary_text(vm,&right,&b);
    ObjString *result = binary_join(vm,left.chars,left.length,right.chars,right.length);
    free(left.buffer.data);
    free(right.buffer.data);
    vm->stack_top -= 2;
    return OBJ_VAL(result);
}
```

### Quand collecter

Reste le seuil. `gc_collect` se termine par cette règle :

```c fichier="src/vm/memory.c" lignes="353-355" fonction="gc_collect"
    vm->next_gc = vm->bytes_allocated * GC_GROW_FACTOR;
    if(vm->next_gc < GC_FIRST_THRESHOLD)
        vm->next_gc = GC_FIRST_THRESHOLD;
```

Après une collecte, la prochaine aura lieu quand la mémoire vivante aura
doublé (`GC_GROW_FACTOR` vaut 2), et jamais en dessous de 16 Mo. C'est la
règle de *Crafting Interpreters* et de beaucoup de GC simples : un programme
qui garde 100 Mo de données vivantes ne paie pas une collecte complète tous
les 16 Mo alloués, et un petit script ne collecte presque jamais.

> [!note]
> `vm_init` (dans `src/vm/vm.c`) fixe le tout premier seuil à 1 Mo
> (`vm->next_gc = 1024 * 1024`), alors que `GC_FIRST_THRESHOLD` vaut 16 Mo
> et que `gc_safepoint` prévoit un seuil de départ à 0. La première collecte
> arrive donc plus tôt que les suivantes ne le voudraient. C'est sans
> conséquence pour la justesse, et c'est une petite incohérence à connaître.

## 11.9 Les chaînes internées, et celles qui ne le sont pas

Les noms sont partout dans la VM : `GET_BUILTIN` cherche `"println"`,
`OP_INVOKE` cherche une méthode, `define_method` compare un nom à `__init__`.
Pour que ces recherches soient rapides, les noms sont **internés** : deux
chaînes de même texte sont un seul objet. Dans `src/vm/object.c` :

```c fichier="src/vm/object.c" lignes="32-42" fonction="string_copy"
ObjString *string_copy(VM *vm, const char *chars, int length){
    uint32_t hash = string_hash(chars,length);
    ObjString *interned = table_find_string(&vm->strings,chars,length,hash);
    if(interned != NULL)
        return interned;

    ObjString *string = string_allocate(vm,length,hash,true);
    memcpy(string->chars,chars,(size_t)length);
    table_set(&vm->strings,string,NONE_VAL);
    return string;
}
```

Avant de créer une chaîne, on la cherche dans `vm->strings`, une table qui
contient toutes les chaînes internées. Si elle existe, on rend l'existante.
Après ça, comparer deux noms revient à comparer deux adresses : c'est le
`fs->locals[i].name == name` du compilateur, le `name == vm->name_init` de
`define_method`. Le hash, calculé une fois à la création (FNV-1a, une boucle
de trois lignes), est rangé dans la chaîne et ne sera jamais recalculé. Java
fait la même chose avec `String.intern()`, Lua interne toutes ses chaînes
courtes, Python ses noms d'identifiants.

`table_find_string` est la seule fonction qui compare vraiment des
caractères : c'est la recherche qui *produit* l'internement. Partout ailleurs,
la table compare des pointeurs.

### Pas les longs textes

Interner coûte : un hash de tout le texte, et une recherche dans la table.
Pour un nom de dix lettres, c'est négligeable. Pour un texte de 3 Mo construit
ligne par ligne, c'est une catastrophe :

```c fichier="src/vm/object.c" lignes="19-21"
// Un texte plus long n'est pas interné : le hacher et le chercher coûterait
// autant que le construire, et `s += "ab"` dans une boucle deviendrait très lent.
#define STRING_INTERN_MAX 32
```

```c fichier="src/vm/object.c" lignes="48-55" fonction="string_new"
ObjString *string_new(VM *vm, const char *chars, int length){
    if(length <= STRING_INTERN_MAX)
        return string_copy(vm,chars,length);

    ObjString *string = string_allocate(vm,length,0,false);
    memcpy(string->chars,chars,(size_t)length);
    return string;
}
```

Un texte de plus de 32 octets construit pendant l'exécution n'est pas interné,
et son hash vaut 0, « pas encore calculé » : on ne le calculera que si ce
texte sert un jour de clé de map. Deux chaînes peuvent alors avoir le même
texte et deux adresses différentes, et l'égalité doit le savoir :

```c fichier="src/vm/object.c" lignes="68-75" fonction="string_equals"
bool string_equals(ObjString *a, ObjString *b){
    if(a == b)
        return true;
    // Deux chaînes internées différentes n'ont jamais le même texte.
    if(a->length != b->length || (a->interned && b->interned))
        return false;
    return memcmp(a->chars,b->chars,(size_t)a->length) == 0;
}
```

Même adresse : égales. Deux internées d'adresses différentes : forcément
différentes, sans lire un caractère. Sinon, on compare les longueurs, puis le
texte.

Une chaîne internée que plus personne n'utilise doit quitter la table, sinon
la table la garderait en vie pour toujours. Ce n'est pas une racine : juste
avant de libérer, le GC retire de `vm->strings` les chaînes qui n'ont pas été
marquées (`gc_remove_white_strings`, dans `memory.c`). Lua appelle ça une
table « faible » : elle référence des objets sans les garder en vie.

### Pourquoi Python gagne sur `texte`

On peut maintenant expliquer les deux lignes du chapitre 9 où Python gardait
l'avantage. `bench/texte.cf` fait :

```ceflo fichier="bench/texte.cf"
// Chaînes : concaténation et parcours
var s = ""
for var i = 0; i < 100000; i += 1 { s += "ab" }
var n = 0
for var c in s { if c == 'a' { n += 1 } }
println(n, " ", s.lenght())
```

Une chaîne CeFlo ne change jamais (chapitre 5). `s += "ab"` crée donc une
nouvelle chaîne, et recopie les `2i` octets de `s` dedans. Au tour 100 000,
on recopie 200 000 octets pour en ajouter deux. Sur toute la boucle, ça fait
environ dix milliards d'octets copiés : la boucle est **quadratique**. Java et
Lua ont le même comportement, et leurs guides conseillent d'utiliser un
`StringBuilder` ou `table.concat`.

Python a les mêmes chaînes immuables, mais il triche. Il compte les références
de chaque objet. Quand il exécute `s += "ab"` et voit que `s` n'a qu'une seule
référence, la variable elle-même, il sait que personne d'autre ne verra la
chaîne changer, et il l'agrandit sur place avec `realloc`. La boucle devient
linéaire. CeFlo a un GC qui marque et balaie : il ne sait pas, à un instant
donné, combien de variables pointent vers une chaîne. Il ne peut pas tricher.
`docs/VM.md` range ce cas dans les limites connues.

## 11.10 Computed goto, et la mesure finale

Il reste le `#ifdef USE_COMPUTED_GOTO` qu'on a laissé de côté. Avec un
`switch`, chaque instruction se termine par `goto next`, qui remonte au
`switch`, qui lit l'opcode suivant et saute au bon `case`. Il y a un seul
endroit du programme où l'on choisit la prochaine instruction. Le processeur
essaie de deviner à l'avance où ira ce saut (c'est la **prédiction de
branchement**), et pour un seul point de saut partagé par soixante-cinq
destinations, il devine mal.

GCC et Clang permettent autre chose, une extension du C qu'on appelle
**computed goto** : prendre l'adresse d'une étiquette avec `&&` et sauter à
une adresse calculée.

```c fichier="src/vm/vm.c" lignes="665-692"
    #ifdef USE_COMPUTED_GOTO
        #define LABEL(op) [op] = &&L_##op
        static void *labels[OP_COUNT] = {
            LABEL(OP_CONSTANT), LABEL(OP_NONE), LABEL(OP_TRUE), LABEL(OP_FALSE),
            LABEL(OP_POP), LABEL(OP_DUP), LABEL(OP_DUP2),
            LABEL(OP_GET_LOCAL), LABEL(OP_SET_LOCAL), LABEL(OP_GET_UPVALUE), LABEL(OP_SET_UPVALUE),
            LABEL(OP_GET_GLOBAL), LABEL(OP_SET_GLOBAL), LABEL(OP_DEFINE_GLOBAL), LABEL(OP_GET_BUILTIN),
            LABEL(OP_CLOSE_UPVALUE), LABEL(OP_CHECK_TYPE),
            LABEL(OP_ADD), LABEL(OP_SUBTRACT), LABEL(OP_MULTIPLY), LABEL(OP_DIVIDE), LABEL(OP_MODULO),
            LABEL(OP_EQUAL), LABEL(OP_NOT_EQUAL), LABEL(OP_LESS), LABEL(OP_LESS_EQUAL),
            LABEL(OP_GREATER), LABEL(OP_GREATER_EQUAL), LABEL(OP_NEGATE), LABEL(OP_NOT), LABEL(OP_TO_BOOL),
            LABEL(OP_JUMP), LABEL(OP_JUMP_IF_FALSE), LABEL(OP_LOOP),
            LABEL(OP_CALL), LABEL(OP_INVOKE), LABEL(OP_CLOSURE), LABEL(OP_RETURN),
            LABEL(OP_LIST), LABEL(OP_MAP), LABEL(OP_GET_INDEX), LABEL(OP_SET_INDEX),
            LABEL(OP_GET_FIELD), LABEL(OP_SET_FIELD), LABEL(OP_FORMAT),
            LABEL(OP_STRUCT), LABEL(OP_METHOD), LABEL(OP_FIELDS_INIT), LABEL(OP_NEW),
            LABEL(OP_TYPE_CALL), LABEL(OP_ENUM),
            LABEL(OP_ITER_PREP), LABEL(OP_ITER_NEXT), LABEL(OP_MATCH_FAIL),
            LABEL(OP_IMPORT), LABEL(OP_IMPORT_NAME), LABEL(OP_IMPORT_VALUE), LABEL(OP_IMPORT_ALL), LABEL(OP_IMPORT_NATIVE),
            LABEL(OP_EXPORT),
            LABEL(OP_SET_LOCAL_POP), LABEL(OP_ADD_LOCAL), LABEL(OP_GET_SELF_FIELD), LABEL(OP_SET_SELF_FIELD),
        };
        #define CASE(op) L_##op
        #define NEXT() goto *labels[READ_BYTE()]
    #else
        #define CASE(op) case op
        #define NEXT() goto next
    #endif
```

`labels` est un tableau d'adresses de code : en case `OP_ADD`, l'adresse de
l'étiquette `L_OP_ADD`. `CASE(OP_ADD)` devient l'étiquette `L_OP_ADD:`, et
`NEXT()` devient `goto *labels[READ_BYTE()]` : lire l'opcode suivant, et sauter
directement à son code. Il n'y a plus de point de passage central. Chaque
instruction a son propre saut vers la suivante, et le processeur apprend des
suites fréquentes : après `GET_LOCAL`, souvent un autre `GET_LOCAL` ; après
`LESS`, presque toujours `JUMP_IF_FALSE`.

C'est pour ça que tout `vm_run` est écrit avec `CASE` et `NEXT` depuis le
début : on peut changer de méthode en une ligne (`USE_COMPUTED_GOTO`), et le
code des instructions ne bouge pas. CPython utilise la même extension, avec la
même astuce de macros. Le tableau est `static` : il est rempli une fois, à la
compilation du C.

Combien ça rapporte ? J'ai compilé une copie de la VM avec la version
`switch` (en remplaçant la condition de `USE_COMPUTED_GOTO` par `#if 0`), et
gardé le meilleur temps sur cinq essais :

```text
              switch   computed goto
fib            0.11        0.10
boucle         0.37        0.31
closures       0.11        0.11
objets         0.20        0.19
```

Entre rien et 16 %. Le gain est réel sur `boucle`, où presque tout le temps
passe à aiguiller des instructions simples. Il disparaît là où les
instructions elles-mêmes travaillent (allouer un objet, appeler une méthode).
C'est une bonne leçon sur les optimisations d'une VM : le gros du gain vient
des choix de conception (une valeur de 16 octets, des noms résolus d'avance),
et les astuces de bas niveau grattent ce qui reste.

## Défis

1. **La trace de la pile.** Ajoute une option `--trace` à `src/vm/main.c` qui
   affiche, avant chaque instruction, le contenu de la pile du cadre courant,
   comme le fait `mini_vm.c`. Commence par un champ `bool trace` dans `VM`
   (`src/vm/vm.h`, à côté de `disassemble`), puis appelle
   `chunk_disassemble_instruction` en haut de la boucle. Avec computed goto,
   il n'y a pas de « haut de la boucle » : regarde où passe `NEXT()`.

2. **La pile des appels.** Quand une erreur arrive dans une fonction appelée
   par une autre, affiche toute la chaîne : `appelé depuis f, ligne 12`,
   `appelé depuis main, ligne 30`. Tout est dans `vm->frames` : `frame_node`
   donne le noeud de chaque cadre. Le point d'entrée est `vm_error`, dans
   `src/vm/vm.c` ; attention, `error_node_v` (`src/error.c`) arrête le
   programme, il faut donc afficher la chaîne avant.

3. **Une instruction de plus.** `i < n` suivi de `JUMP_IF_FALSE` est la paire
   la plus fréquente de toutes les boucles. Ajoute `OP_JUMP_IF_NOT_LESS`, qui
   compare les deux valeurs du sommet et saute si `a < b` est faux, sans
   fabriquer de booléen. Il faut toucher `chunk.h`, `debug.c`,
   `compile_condition` (`src/vm/compiler.c`) et `vm_run`. Mesure avec
   `make bench` : gagne-t-on quelque chose sur `boucle` ?

4. **Le seuil du GC.** Fais afficher à `gc_collect` (`src/vm/memory.c`) le
   nombre d'octets avant et après chaque collecte, sur `stderr`, et lance
   `bench/listes.cf`. Combien de collectes ? Change `GC_GROW_FACTOR` en 4,
   puis en 1, et mesure le temps et la mémoire (`/usr/bin/time -v` donne le
   « Maximum resident set size »).

## Note de conception

### Garder l'ancien interpréteur

Quand on a décidé de réécrire CeFlo en bytecode, la tentation était de jeter
le visitor. Il était lent, il allouait chaque nombre, il cherchait chaque nom :
tout ce qu'on voulait laisser derrière nous. On l'a gardé, compilé à côté sous
le nom `Ceflo_ref`, et c'est probablement la meilleure décision de toute la
réécriture.

Une VM se trompe d'une façon particulière. Elle ne plante pas : elle donne un
résultat légèrement faux. Un `+=` qui lit la variable au mauvais moment, un
`break` qui oublie un `POP` et décale toutes les cases suivantes, un `match`
qui ne lève pas son erreur. Les tests qu'on écrit à la main attrapent les cas
auxquels on a pensé. Les autres passent.

Avec un interpréteur de référence, chaque programme devient un test. `make
diff` lance chaque test et chaque exemple du dépôt avec les deux
interpréteurs, et compare les sorties octet par octet, messages d'erreur
compris. `bench/run.sh` refuse un temps dont la sortie diffère. La règle est
écrite dans `docs/VM.md` : quand les deux ne sont pas d'accord, c'est la VM
qui a tort. Les quelques différences voulues (le `+=` qui lit d'abord, les
erreurs trouvées à la compilation) sont listées une par une, et chacune a été
une décision, pas une surprise.

Les langages sérieux font pareil, à plus grande échelle. PyPy compare son
comportement à CPython ; les moteurs JavaScript partagent la suite test262 ;
GCC et Clang se servent l'un de l'autre pour trouver des bugs. On appelle ça
du test différentiel, et c'est la façon la moins chère de vérifier un
programme dont on ne connaît pas toutes les sorties attendues.

Il y a un prix : l'ancien code reste dans le dépôt, il faut le compiler, et un
nouveau venu peut se demander lequel des deux est le vrai. Je crois que c'est
un prix minuscule. Un interpréteur simple et lent, qu'on comprend en entier,
est le meilleur juge qu'on puisse donner à un interpréteur rapide qu'on
comprend moins bien. Si tu écris ton propre langage un jour, écris d'abord le
visitor, garde-le, et ne passe au bytecode qu'avec lui à côté.

14.1 Un programme en plusieurs fichiers

Tous les programmes de ce livre tenaient dans un fichier. Un vrai programme, non. Il a ses outils dans un fichier, ses structures dans un dossier, et il lit le disque avec des fonctions qu'il n'a pas écrites. Voici trois fichiers, rangés dans livre/essais/chapitres-12-14/modules/ :

Et la dernière ligne affiche 0, alors que double vient d'augmenter appels : on y reviendra, c'est le détail le plus instructif du chapitre.

  1. charger un fichier une seule fois, et en faire un module (14.2) ;
  2. copier ses noms dans le fichier qui l'importe, avec export (14.3) ;
  3. les builtins, ces fonctions C visibles partout (14.4) ;
  4. les méthodes C des listes, des maps et des chaînes (14.5) ;
  5. les modules os et console, écrits en C mais importés comme un fichier (14.6) ;
  6. une bibliothèque .so qu'on écrit soi-même et qu'on charge pendant l'exécution (14.7).

Puis on fera les comptes : ce qu'on a construit en quatorze chapitres, ce que ça vaut face à Python, et comment écrire ton propre langage (14.8 et 14.9).

14.2 Un fichier, un module, une seule fois

Un module est un ObjModule. On l'a construit au chapitre 10 pour ranger les globales d'un fichier : un tableau de valeurs, le nom de chaque case, son type, sa constance, et une table du nom vers le numéro. Deux champs restaient inutilisés, exports et loaded. Ils servent maintenant.

Le fichier lancé depuis la ligne de commande est déjà un module : vm_run_file appelle run_source, dans src/vm/module.c. Un fichier importé passera par la même fonction :

C'est toute la chaîne du livre en six lignes : le parser, le compilateur, la closure du code du fichier, et vm_call qui l'exécute dans une boucle vm_run à elle. Un import est un appel de fonction comme un autre : la VM est réentrante (chapitre 11), et le fichier importé tourne au-dessus de celui qui l'importe, sur la même pile.

vm->modules est une Table du chemin vers le module. C'est elle qui garantit qu'un fichier ne s'exécute qu'une fois. Regarde où est le table_set : avant compile_module et vm_call. On aurait pu le mettre à la fin, une fois le fichier fini. Ce serait une erreur, à cause de ce cas :

a importe b, qui importe a. Si a n'était rangé qu'à la fin, b chargerait a une deuxième fois, qui chargerait b, et ainsi de suite jusqu'à « trop d'appels imbriqués ». Rangé dès le début, a est trouvé dans la table par b, à moitié exécuté : sa première ligne est faite, nom_a n'existe pas encore. b reçoit donc ce qui est défini, c'est-à-dire rien, et l'erreur est claire. L'ancien interpréteur donne exactement la même sortie.

Python se comporte de la même façon : un module est rangé dans sys.modules avant d'être exécuté, et un import circulaire voit un module « partiellement initialisé ». Node.js aussi, avec ses require qui retournent un objet incomplet. C'est le prix d'une règle simple, et les trois langages l'ont choisie.

Trouver le fichier

OP_IMPORT appelle module_import avec le chemin écrit dans le code :

L'ordre des essais est la règle de GRAMMAIRE.md : un fichier trouvé passe avant un module fourni par CeFlo. newLexer ouvre le fichier (chapitre 1) et retourne false s'il n'existe pas ; alors seulement on demande à natives_standard_module si os.cf ou console.cf est un module écrit en C (section 14.6). Un fichier os.cf à côté du script cache donc le module os.

resolve_path (lignes 53 à 74) essaie d'abord le chemin à côté du fichier qui importe. Elle le trouve grâce au noeud de l'instruction en cours, vm_current_node(vm), dont le champ file est le nom du fichier : c'est la même information qui sert à afficher les erreurs depuis le chapitre 1. Si le fichier n'est pas là, le chemin est gardé tel quel, et newLexer le cherchera depuis le dossier courant.

Un détail : la clé de vm->modules est le chemin résolu. Deux fichiers de dossiers différents qui écrivent from outils import * désignent deux outils.cf différents, et chacun aura son module. Mais un même fichier atteint par deux chemins écrits différemment (outils.cf et ./outils.cf) serait chargé deux fois. Python règle ça en rangeant ses modules par nom qualifié, geo.point, plutôt que par chemin.

À toi

Lance ./Ceflo modules/principal.cf depuis livre/essais/chapitres-12-14/, au lieu de te placer dans modules/. Tout marche encore : le chemin est cherché à côté du fichier qui importe. Puis écris dans principal.cf un import de "./outils.cf" en plus de celui de outils. Combien de fois outils.cf s'exécute-t-il ?

14.3 Copier les noms

OP_IMPORT pose le module sur la pile. Il faut maintenant que double, dans principal.cf, désigne la fonction de outils.cf. Le compilateur ne connaît pas outils.cf : il ne l'a pas encore lu, et il ne le lira peut-être jamais s'il est déjà chargé. Il fait donc de double une globale de principal.cf, comme n'importe quel nom inconnu, et c'est la VM qui la remplira au moment de l'import. On ajoute à compiler.c, dans la section $MODULES :

Trois formes, trois façons de faire. Commençons par la plus fréquente, en bas : un import par noms au niveau du fichier. Pour chaque nom, global_index crée la case dans le module courant (la case 0 pour double, la case 1 pour VERSION), et OP_IMPORT_NAME la remplira. Le module reste sur la pile pendant tous les noms, et un POP final le retire. C'est le IMPORT, IMPORT_NAME, IMPORT_NAME, POP du désassemblage :

                          pile                globales de principal.cf
IMPORT "outils.cf"        [ outils ]          double = ?   VERSION = ?
IMPORT_NAME "double"      [ outils ]          double = <func double>
IMPORT_NAME "VERSION"     [ outils ]          VERSION = "1.0" (constante)
POP                       [ ]

add_file_name a un rôle qu'on reverra en 14.4 : un nom importé cache un builtin du même nom.

Côté VM, OP_IMPORT_NAME appelle module_import_name, qui cherche le nom puis le copie :

copy_global copie trois choses : la valeur, le type et la constance. VERSION reste donc une constante dans principal.cf, et VERSION = "2.0" y serait refusé. Un var age::int importé garde son type. Les deux erreurs de find_export se voient ainsi :

La flèche pointe sur le nom, pas sur from : le compilateur a donné à chaque OP_IMPORT_NAME le noeud de son nom. last_import_path garde le chemin tel qu'il est écrit, pour que le message dise outils.cf et pas un chemin résolu qui commencerait par un dossier.

Une copie, pas un lien

On peut maintenant expliquer le 0 de la section 14.1. from outils import [appels] a copié la valeur de appels au moment de l'import, quand elle valait 0. Ensuite, double(21) exécute le code de outils.cf, qui lit et écrit la globale appels de son module, avec GET_GLOBAL et SET_GLOBAL sur ses propres cases. La case appels de principal.cf n'en sait rien.

module outils.cf                     module principal.cf
+---------------------+              +---------------------+
| VERSION  "1.0"      |  copie à     | double   <func>     |
| appels   1   <------+-- l'import --| VERSION  "1.0"      |
| double   <func>     |   (valait 0) | appels   0          |
| secret   <func>     |              | Point    <struct>   |
+---------------------+              +---------------------+

Python fait exactement pareil : from outils import appels copie la valeur, et il faut écrire import outils puis outils.appels pour lire la valeur à jour. JavaScript a fait l'autre choix : un import { appels } des modules ES6 est un lien vivant, et appels suit les changements du module. Ça demande, pour chaque nom importé, une indirection de plus à chaque lecture. CeFlo a pris la règle de Python, qui coûte une copie une fois, et rien ensuite : double dans principal.cf est un GET_GLOBAL comme un autre.

import *

OP_IMPORT_ALL copie tout ce qui est exporté :

Trois sortes de cases sont sautées : celles qui ne sont pas encore définies (un nom seulement lu par le module, ou le module à moitié exécuté de a.cf), le main du module (sinon le main d'un module importé remplacerait celui du fichier, et GRAMMAIRE.md dit qu'il ne se lance jamais), et ce qui n'est pas exporté.

export est une instruction exécutée, OP_EXPORT, et pas une déclaration lue par le compilateur. Elle vérifie que le nom existe au moment où elle s'exécute : c'est pour ça que export :: [...] s'écrit à la fin du fichier, après les définitions, et que le parser refuse un export dans un bloc.

import * a un coût caché pour le compilateur. Après lui, n'importe quel nom peut devenir une globale, puisqu'on ne sait pas ce que le module contient. Le compilateur pose has_import_all, et ne fait plus confiance à sa liste des builtins : dans principal.cf, println est un GET_GLOBAL 3, pas un GET_BUILTIN. La VM se débrouille à l'exécution, on le verra en 14.4.

Un import dans une fonction

La forme du milieu de compile_include traite un import écrit dans un bloc. Le module attend dans une case cachée, et chaque nom devient une locale :

IMPORT pose le module dans la case 1. GET_LOCAL 1 le recopie au sommet, et IMPORT_VALUE remplace cette copie par la valeur de double, qui devient la case 2. Le deuxième appel de calcule refait l'IMPORT, mais trouve le module dans vm->modules : outils.cf ne s'exécute qu'une fois. 14.4 Les builtins

println n'est défini dans aucun fichier. C'est un builtin : une fonction écrite en C, visible depuis tous les fichiers sans import. On les range dans une table de la VM, vm->builtins, remplie par vm_init avant toute compilation. Chaque entrée est un ObjNative, l'objet du chapitre 11 qui enveloppe un pointeur de fonction C :

La forme d'une native mérite qu'on s'y arrête, parce que c'est celle de toutes les fonctions C de ce chapitre, jusqu'aux bibliothèques .so. Elle reçoit la VM, le nombre d'arguments, et un pointeur sur le premier argument. Ce pointeur est dans la pile de la VM : on ne copie rien pour appeler une native. Le cas OBJ_NATIVE de call_value le montre :

println("a", 1)          [ ...  println  "a"  1 ]
                                         ^ args = stack_top - 2,  argc = 2
après l'appel            [ ...  none ]

La native lit args[0] et args[1], retourne sa valeur, et la VM remplace la fonction et ses arguments par le résultat. return false dit qu'aucun CallFrame n'a été ouvert : la boucle continue dans la même fonction.

Lua fait la même chose avec sa pile, mais une fonction C y reçoit un lua_State et lit ses arguments avec lua_tonumber(L, 1). CPython passe un tableau de PyObject* depuis Python 3.8, la convention « vectorcall », pour la même raison que nous : ne pas fabriquer un tuple à chaque appel.

14.5 Les méthodes de list, map et str

liste.append(4) et texte.split(",") ressemblent à des appels de méthodes, et le compilateur les traite comme tels : c'est un OP_INVOKE (chapitre 13). Mais une liste n'est pas un objet d'une structure, et elle n'a pas de table de méthodes. On l'a vu au chapitre 13 : invoke finit par appeler natives_call_method, dans src/vm/natives/methods.c.

Une méthode native a presque la forme d'une native, avec un paramètre de plus, l'objet :

Il y a une table par type (lignes 261 à 295) : sept méthodes pour une liste, huit pour un map, une pour une énumération, quatre pour une chaîne. lenght et length y sont deux entrées qui pointent sur la même fonction : la faute de frappe historique de CeFlo (lenght) est restée, et l'orthographe juste a été ajoutée à côté. La recherche, elle, a une petite astuce :

Les noms des méthodes sont des textes C, pas des chaînes internées : on ne peut pas les comparer par adresse. Au premier appel, method_find calcule le hash et la longueur de chaque nom de la table, une fois pour toute la durée du programme. Ensuite, chercher append revient à comparer des nombres : le hash du nom demandé (déjà calculé, puisque c'est une chaîne internée) avec sept hashes. Le memcmp final ne sert qu'à confirmer, et il ne tourne presque jamais sur un mauvais nom.

On aurait pu ranger ces méthodes dans une Table de la VM, avec des clés internées, comme les méthodes d'une structure. Ce serait un peu plus rapide pour un type qui en a beaucoup. Avec sept méthodes au plus, la boucle sur un petit tableau est aussi rapide, et elle reste lisible : ajouter une méthode, c'est écrire la fonction et une ligne dans la table.

Une native qui rappelle du CeFlo

La plupart des méthodes ne font qu'un calcul en C. filter est différente : elle appelle la fonction CeFlo qu'on lui donne, pour chaque élément. Et c'est ici que la règle du GC du chapitre 11 trouve sa seule exception :

vm_call exécute du CeFlo, qui passe par des points sûrs : un appel, un retour, un tour de boucle. Le GC peut alors tourner, et il ne voit que ses racines. La nouvelle liste result n'est sur aucune pile et dans aucune globale : sans vm_protect, elle serait libérée au premier GC, et le list_append suivant écrirait dans de la mémoire rendue. vm_protect range l'adresse de la variable C dans vm->roots, que gc_mark_roots parcourt.

self et function sont en fait déjà en sécurité : ce sont des valeurs de la pile de la VM, posées par l'appelant, et elles y restent pendant tout l'appel. Les protéger ne coûte rien et évite de devoir y réfléchir. On reverra ce bug, pour de vrai, avec une bibliothèque .so en 14.7.

Le deuxième commentaire est un détail du vrai code : la taille de la liste est relue à chaque tour, parce que la fonction appelée peut ajouter ou enlever des éléments. Une boucle qui garderait count dans une variable lirait au-delà de la fin si la fonction vidait la liste.

À toi

Ajoute une méthode map(f) aux listes, qui retourne une nouvelle liste avec f(x) pour chaque élément. Copie method_list_filter, change deux lignes, et ajoute une entrée dans Method_List. Teste-la avec une lfunc qui contient une boucle, pour que le GC ait une chance de tourner, puis compile ta copie avec -DCEFLO_GC_STRESS et retire un vm_protect pour voir ce qui arrive.

14.6 os et console

from os import [lire] passe par module_import comme un fichier. Le parser a fait de os le chemin "os.cf", newLexer ne trouve aucun fichier de ce nom, et natives_standard_module prend le relais :

C'est l'idée qui rend ce morceau si court : un module écrit en C est un ObjModule comme les autres, dont chaque globale est une ObjNative. Pour la suite de la VM, il n'y a aucune différence. OP_IMPORT_NAME, copy_global et find_export marchent sans changer une ligne, et from os import * aussi. On aurait pu inventer une syntaxe à part, ou un objet os avec des attributs. On a préféré qu'un module fourni par CeFlo ne se distingue en rien d'un module écrit par l'utilisateur.

Le module est rempli une fois, au premier import, puis gardé dans vm->native_modules. Un script qui n'importe jamais os ne paie rien : pas une ObjNative n'est créée.

La ligne vide à la fin est réelle : la sortie de wc se termine par un retour à la ligne, que commande garde.

Pas d'exceptions

lire_lignes d'un fichier absent ne s'arrête pas : il retourne none. C'est la règle écrite en tête de os.c : CeFlo n'a pas d'exceptions, et un échec attendu (un fichier absent, un dossier qu'on ne peut pas créer) est une valeur que le script teste. Seule une mauvaise utilisation, comme lire(3), arrête le programme. Les fonctions d'os.c suivent donc toutes le même plan, qu'on voit dans os_lire :

D'abord vérifier les arguments, et arrêter le programme s'ils sont faux. Puis faire l'appel système, et retourner none s'il échoue. Enfin fabriquer la valeur CeFlo. os_text (ligne 22) ajoute une vérification qu'on oublierait sûrement : une chaîne CeFlo peut contenir un \0, et un chemin C s'arrête au premier. lire("a.txt\0.cf") ouvrirait a.txt sans le dire. os_text refuse ce cas.

Go fait le même choix que CeFlo, avec des valeurs d'erreur retournées en plus du résultat. Python et Java lèvent des exceptions. Lua fait les deux : io.open retourne nil et un message, error lève une erreur. Pour un langage dont la VM doit se lire en un après-midi, ne pas avoir d'exceptions évite tout un mécanisme : dérouler la pile, fermer les upvalues en chemin, retrouver le bon CallFrame.

console

console est construit de la même façon, avec sa table Console_List dans src/vm/natives/console.c : clrscr, getch, getchar, kbhit et sleep. C'est le module du jeu du serpent de exemple/. Ses fonctions mettent le terminal en mode brut (sans écho, sans attendre la touche Entrée) avec termios, et un détail du vrai code mérite d'être lu : console_raw_on installe un gestionnaire pour SIGINT, pour qu'un Ctrl+C pendant getch ne laisse pas le terminal de l'utilisateur sans écho.

14.7 Écrire une bibliothèque .so

Tout ce qu'on a vu jusqu'ici est compilé dans ./Ceflo. Pour ajouter une fonction C, il fallait recompiler l'interpréteur, comme pour horloge. Une bibliothèque partagée (un .so sous Linux, un .dylib sous macOS, un .dll sous Windows) permet de charger du code C pendant l'exécution, sans toucher à l'interpréteur. C'est ce que fait from @"lib/math/libmath.so" import [mathSqrt]. On va en écrire une, la compiler, et la charger.

Ce qu'inclut une bibliothèque

Une bibliothèque n'inclut qu'un fichier, src/vm/ceflo.h :

Avec vm.h, elle reçoit tout le contrat : Value et ses macros, les objets, vm_call, vm_protect, vm_error. Une fonction exportée a la forme d'une native : Value f(VM *vm, int argc, Value *args). C'est la troisième différence voulue de docs/VM.md : les bibliothèques de l'ancien interpréteur avaient une autre forme, et celles de lib/ ont été réécrites.

On compile avec les options du Makefile pour lib/, depuis livre/essais/chapitres-12-14/libmots/ :

-shared produit une bibliothèque au lieu d'un programme. -fPIC (position independent code) produit du code qui marche à n'importe quelle adresse : le système ne sait pas à l'avance où il chargera la bibliothèque. Les deux -I donnent les en-têtes de la VM, dans cet ordre : src/vm passe avant src/include, parce que sur macOS value.h et Value.h (celui du visitor) sont le même nom de fichier (Makefile, lignes 19 et 20).

Et l'erreur pointe sur la ligne 7 du script, alors qu'elle est née dans une fonction C d'une bibliothèque : vm_error lit le noeud de l'instruction en cours, comme partout.

Attention

J'ai d'abord écrit from @"libmots.so", sans ./, et obtenu « impossible d'ouvrir libmots.so : libmots.so: cannot open shared object file ». Un chemin sans / est cherché par dlopen dans les dossiers du système (LD_LIBRARY_PATH, /usr/lib...), jamais dans le dossier courant. Le chemin à côté du script n'est essayé que si le script est lui-même dans un dossier.

Comment la VM charge la bibliothèque

Le compilateur fait de chaque nom importé un OP_IMPORT_NATIVE, avec le chemin et le nom (compile_include, lignes 1503 à 1516), puis range la valeur comme une variable. La VM appelle natives_load_library, dans src/vm/natives/library.c :

library_open (lignes 90 à 111) appelle dlopen une fois par bibliothèque, et garde le résultat dans un tableau : importer dix fonctions d'un même .so ne l'ouvre qu'une fois. dlsym cherche ensuite la fonction par son nom, et retourne son adresse.

Les lignes 121 et 122 sont une curiosité du C. dlsym retourne un void*, un pointeur vers des données. Le standard C ne permet pas de convertir un pointeur de données en pointeur de fonction : sur certaines machines, les deux n'ont même pas la même taille. POSIX garantit que ça marche pour dlsym, mais gcc -Wpedantic se plaindrait d'un simple cast. Le memcpy copie les octets sans conversion, et le compilateur le réduit à une affectation.

native_names garde une copie du nom, qui vivra jusqu'à la fin du programme. ObjNative ne garde qu'un const char*, et name->chars appartient à une chaîne que le GC peut libérer. natives_free libère ces copies et ferme les bibliothèques à la fin, après les objets.

-rdynamic

Une question doit te travailler depuis le début de la section : libmots.so appelle native_check_args et list_new, qui sont dans ./Ceflo. Comment la bibliothèque les trouve-t-elle ? Elle ne les contient pas, et on ne l'a liée à rien. Par défaut, un programme n'expose pas ses fonctions aux bibliothèques qu'il charge. Pour le voir, j'ai compilé la VM sans l'option qui change ça :

L'option est dans LDFLAGS, ligne 15 du Makefile :

LDFLAGS = -rdynamic -lm -ldl

-rdynamic demande à l'éditeur de liens de mettre toutes les fonctions du programme dans sa table de symboles dynamiques. Au dlopen, les symboles manquants de la bibliothèque sont cherchés là. Sous macOS, l'éditeur de liens refuse même de produire une bibliothèque qui a des symboles inconnus : il faut lui dire -undefined dynamic_lookup (Makefile, lignes 49 à 52). -ldl apporte dlopen et dlsym sur les anciennes versions de la glibc.

C'est le modèle de Lua et de Python : une extension C appelle les fonctions de l'interpréteur qui la charge. L'autre modèle, celui de Node.js avec son API N-API, passe une table de pointeurs de fonctions à l'extension, qui n'a alors besoin d'aucun symbole. C'est plus portable, et beaucoup plus de code à écrire.

Avec une lfunc simple comme x * x, le bug ne se montre même pas en mode stress : une fonction sans boucle ni appel retourne avant tout point sûr (OP_RETURN d'une boucle vm_run relancée par vm_call sort avant son SAFEPOINT). C'est la raison pour laquelle un test doit appeler du code qui boucle.

À toi

Ajoute à libmots une fonction mots_compte(texte, carac) qui retourne le nombre de fois où le caractère apparaît. Un char CeFlo se vérifie avec "char" et se lit avec AS_CHAR. Compile, importe, et vérifie qu'un appel avec une chaîne à la place du caractère donne un message clair.

14.8 Ce qu'on a construit

Fais le compte. Un lexer, un parser à descente récursive et un arbre, communs aux deux interpréteurs : 1 913 lignes de C. Un interpréteur qui parcourt l'arbre, avec ses portées, son GC et ses modules : 3 514 lignes. Une machine virtuelle complète, avec son compilateur, son GC, ses closures, ses objets, ses modules et toutes ses natives : 7 413 lignes. Aucune dépendance, sinon la bibliothèque standard du C et dlopen.

Et la vitesse. Voici make bench, lancé une seule fois au début de l'écriture de ce chapitre, sur ma machine (le meilleur de trois essais pour chaque programme, et la sortie comparée à celle de l'ancien interpréteur) :

Le chapitre 9 commençait sur un constat : le visitor était trois fois plus lent que Python. La VM est maintenant plus rapide que Python sur neuf programmes sur dix, de 1,1 fois sur texte à 4,1 fois sur closures. Elle va de 1,3 à 16,9 fois plus vite que le visitor. fib(30), 2,7 millions d'appels de fonction, prend 0,09 s.

Chaque ligne du tableau se relie à un chapitre. listes (16,9 fois) est le gain des valeurs de 16 octets du chapitre 9 : plus aucun nombre n'est alloué. closures (6,2 fois, et 4,1 fois Python) mesure les upvalues du chapitre 12 : un compteur appelé un million de fois lit et écrit sa variable par un pointeur. methodes et objets mesurent le chapitre 13 : les attributs à place fixe et OP_INVOKE. boucle et fib mesurent le chapitre 11, la boucle d'exécution et ses computed goto.

Ce qui reste à faire

La ligne gros_texte est la seule où Python gagne, et de loin : 1,99 s contre 0,15 s. C'est la dernière limite de docs/VM.md. Le programme construit un texte de 30 000 lignes avec texte += l + "\n". Une chaîne CeFlo ne change jamais : chaque += crée une nouvelle chaîne et recopie tout le texte d'avant. Le travail croît comme le carré du nombre de lignes. CPython triche intelligemment : quand une chaîne n'a qu'une seule référence (il le sait grâce à son comptage de références), il l'agrandit sur place. Java et Lua ont le même problème que CeFlo, et le résolvent dans la bibliothèque, avec StringBuilder et table.concat. CeFlo pourrait faire l'un ou l'autre : une méthode join sur les listes, ou un objet buffer. C'est le premier défi de ce chapitre.

Le reste de la liste est dans docs/VM.md et dans ces quatorze chapitres : une locale déclarée plus bas qu'une lfunc qui la lit (chapitre 12), le match qui ne sait pas reconnaître une énumération à la compilation (chapitre 13), un import * dans un bloc qui va dans les globales. Et ce que CeFlo n'a pas du tout : des exceptions, des bibliothèques sous Windows, un débogueur pas à pas, un client HTTP. Aucune de ces choses ne demande de nouvelle idée. Tu as déjà vu chacune des pièces qu'elles utiliseraient.

14.9 Écrire ton propre langage

Tu as lu un langage entier, du premier caractère lu par lexer_advance jusqu'au dlsym d'une bibliothèque. Pour écrire le tien, tu n'as pas besoin de refaire le chemin dans le même ordre que CeFlo. CeFlo a été écrit deux fois, d'abord en visitor, puis en bytecode, parce que c'est ainsi qu'il a vraiment été construit. Toi, tu peux choisir. Voici l'ordre que je conseillerais, avec la taille de chaque étape dans CeFlo pour te donner une idée.

  1. La grammaire, sur une page. Avant toute ligne de C, écris ton GRAMMAIRE.md. Celui de CeFlo tient en une centaine de lignes pour les règles. Chaque règle deviendra une fonction du parser : si la grammaire est confuse, le parser le sera.
  2. Le lexer et le parser, jusqu'à afficher l'arbre. C'est 1 900 lignes dans CeFlo, messages d'erreur compris. Ne passe pas à la suite tant que l'arbre affiché n'est pas exactement celui que tu attends, et tant que chaque erreur de syntaxe ne pointe pas le bon caractère.
  3. Un visitor, pour avoir un langage qui marche. C'est le chemin le plus court vers un programme qui tourne, et il te servira de référence pour toujours, comme Ceflo_ref sert à make diff. Garde-le petit.
  4. Les tests, tout de suite. Un dossier de .cf et de .out, et un script de trente lignes comme tests/run.sh. Chaque bug corrigé devient un test. Les 218 tests de CeFlo ont permis de réécrire tout l'intérieur sans casser le langage.
  5. Le bytecode, si tu as besoin de vitesse. Les quatre idées de docs/VM.md font presque tout le gain : une valeur qui se copie, des noms résolus à la compilation, des attributs à place fixe, un GC qui ne tourne qu'aux points sûrs. Commence par les deux premières.

Quelques conseils, que ce livre a appris à ses dépens :

  • Écris le désassembleur avant la VM. --dis a servi à chaque chapitre de la partie 3. Un bug de compilateur se voit dans le bytecode bien avant qu'il ne fasse planter la VM.
  • Fais tourner le GC tout le temps pendant les tests. Le bug de la section 14.7 aurait attendu des mois. CEFLO_GC_STRESS le trouve en une seconde.
  • Garde les erreurs aussi bonnes que le langage. Un message qui dit la ligne, la colonne et ce qui était attendu vaut plus qu'une fonctionnalité de plus. Chaque octet de bytecode de CeFlo garde son noeud pour ça.
  • Copie sans honte. La pile de CeFlo, ses upvalues et son OP_INVOKE viennent de Lua et de Crafting Interpreters. Ses modules ressemblent à ceux de Python. Ce qui fait un langage, c'est l'ensemble des choix, pas l'originalité de chaque pièce.

Si tu veux aller plus loin, trois lectures. Crafting Interpreters de Robert Nystrom, en accès libre sur craftinginterpreters.com, construit deux fois le même langage, comme ce livre. Le code source de Lua 5.4, environ 30 000 lignes de C très lisibles, montre une VM à registres au lieu d'une pile. Engineering a Compiler de Cooper et Torczon, pour le jour où tu voudras optimiser le code produit.

Et surtout, commence petit. Le premier programme de ton langage n'a pas besoin de structures ni de modules. Il a besoin d'afficher 3 quand on écrit 1 + 2. Tout le reste de CeFlo est venu après.

Défis

  1. Défi 1

    join. Ajoute aux listes une méthode join(sep) qui assemble des chaînes en une seule, avec une seule allocation : calcule d'abord la longueur totale, puis remplis une chaîne de string_reserve. Réécris bench/gros_texte.cf avec lignes.join("\n") (dans une copie) et relance bench/run.sh sur ce seul programme. Regarde method_list_filter pour la forme, et format dans vm.c pour le remplissage.

  2. Défi 2

    Un module temps. Fais de horloge un module à part, from temps import [horloge, date], comme os et console. Il faut une table Temps_List, une branche dans natives_standard_module, et rien d'autre dans la VM. date() peut retourner un map { annee, mois, jour } construit avec map_new et map_set.

  3. Défi 3

    import outils sans from. Ajoute la forme import outils, qui donne le module lui-même dans une variable, et outils.double(2). Le module doit alors répondre à OP_GET_FIELD et à OP_INVOKE : ajoute un cas IS_MODULE dans get_field_slow et dans invoke, qui lit la globale exportée. Tu auras un lien vivant : outils.appels suivra les changements. Il faut aussi toucher le parser (parser_parse_include) et la grammaire.

  4. Défi 4

    Des bibliothèques qui s'enregistrent. Aujourd'hui, chaque nom importé d'un .so est cherché avec dlsym. Fais que library_open cherche aussi une fonction ceflo_init(VM *vm) dans la bibliothèque, et l'appelle si elle existe : la bibliothèque pourrait y définir des builtins avec vm_define_builtin, ou préparer un état. Pense à ce qui se passe si deux fichiers importent la même bibliothèque.

Note de conception

pourquoi c'est fait comme ça

Ce chapitre a ouvert CeFlo au C de trois façons : les builtins compilés dans l'interpréteur, les modules os et console qui ressemblent à des fichiers, et les bibliothèques .so chargées à la demande. Toutes les trois reposent sur une seule forme de fonction, Value f(VM *vm, int argc, Value *args), et c'est le choix de ce chapitre qui compte le plus.

Une interface C est un contrat qu'on ne peut plus changer. Le jour où des gens auront écrit des bibliothèques pour ton langage, chaque changement de Value ou de vm_call les cassera. Python porte encore les choix de son API C des années 1990 : le comptage de références qu'on ne peut pas retirer, le verrou global qu'on a mis vingt ans à rendre facultatif. Lua a choisi l'inverse : une bibliothèque ne voit jamais une valeur Lua, seulement des index dans une pile, et l'intérieur de la VM a pu changer complètement d'une version à l'autre sans casser les extensions.

CeFlo a fait le choix de Python, et je pense que c'était le bon choix pour lui. Une bibliothèque CeFlo lit AS_STRING(args[0])->chars directement, sans une couche d'appels à traverser, et une bibliothèque de quarante lignes comme libmots se lit sans rien connaître d'autre que object.h. Le prix est écrit en tête de docs/VM.md : les bibliothèques de l'ancien interpréteur ont dû être réécrites. Un langage qui a peu d'utilisateurs peut se permettre de casser son contrat. Un langage qui en a beaucoup ne le peut plus, et c'est pourquoi les grands langages paraissent si prudents.

Si tu écris ton propre langage, pose-toi la question tôt, avant la première bibliothèque écrite par quelqu'un d'autre. Et fais comme CeFlo : un seul en-tête à inclure, ceflo.h, qui dit exactement ce qu'une bibliothèque a le droit d'utiliser. Tout ce qui n'y est pas pourra changer.
